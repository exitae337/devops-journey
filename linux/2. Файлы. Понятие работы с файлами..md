
В ***Windows*** - файл для нас, это объект, который позволяет организовать структуру хранения данных. У меня есть носитель, там хранятся данные разного типа. Данные имеют разные типы и имена. Мы относимся к файлам как к способу структурированного хранения данных.

В понимании Linux - файл это некоторый универсальный интерфейс к любому фрагменту, потоку данных. При помощи такого вот некоторого универсального объекта обеспечивается интерфейс к данным, которые у нас сохранены на носителе, и к данным, которые являются структурами ядра и к данным которые могут быть получены или переданы через тот или иной порт (или устройства). То есть файл становится некоторым универсальным средством доступа к тем или иным потокам данных. Это же определяет концепцию разделения на некоторые типы.

Какие файлы бывают. Фактически можно выделить три группы.

1. Регулярные файлы
2. Каталоги
3. "Дырки". File-holes

#### Регулярные файлы

Это как раз те файлы, которые являются фрагментами данных, сохраненные в памяти и имеющие уникальное имя. В Linux традиционно используются файловые системы, которые используют индексные дескрипторы. Весь раздел носителя информации, где мы хотим "создать" файловую систему, после ее создания разбивается на некоторое количество областей. Одна из этих областей - область i-node (Область индексных дескрипторов). И также самая большая область - data. Область i-node представляет из себя совокупность фрагментов данных одинакового размера - дескрипторы файлов (i-node). Дескриптор файла хранит в себе все метаданные, сведения включая историю, права, размер и другие - и в том числе определенным способом при помощи i-node хранятся данные о размещении содержимого в области data. С этой точки зрения в Linux файл - это есть этот i-node (сквозная нумерация). Этот номер однозначно идентифицирует файл. Если мы прочитаем индексный дескриптор - мы сможем узнать все о файле.

#### Каталог. Ссылки

Хранить файлы просто в некотором пространстве без структуры плохо (особенно когда файлов становится слишком много). Нужна иерархия. Как раз таки обеспечение структуры было предложено делать при помощи каталогов. Таблица, которая по факту содержит два столбца (также она может быть сложнее, с доп. столбцами, но об этом потом) - имя файла и его i-node. 

Если например мы напишем команду

``` bash
echo "text" > file
```

То в файле, который является каталогом появится запись в таблице. Имя "file" и некий i-node. Запись про i-node ссылается на некоторый из фрагментов в области файловых дескрипторов.

 Как только мы сделали вывод команды, ОС работая в своем компоненте управления файловой системой: 
 
 1. Поняла что надо сохранить файл
 2. Нашла свободный i-node определенным образом
 3. Нашла и выделила свободный блок
 4. Записала в блок data - данные
 5. В i-node указала где эти данные искать
 6. Заполнила metadata
 7. В каталоге создала запись из имени и файлового дескриптора.

Вот эта запись в каталоге имеет понятие - жесткая ссылка. То есть уже при создании файла мы создаем жесткую ссылку (без команды `ln`). Сам файл - это его индексный дескриптор, а имя, которое появилось в каталоге - способ доступа к этому файлу. При создании файла мы создаем на него **первую** жесткую ссылку в виде записи в каталоге.

В Linux файл и каталог и "дырка" - это все файл. Просто этот файл имеет специфический тип, который хранит таблицу. Это также определяет то, что нельзя создать в одном каталоге файл и подкаталог с одним и тем же именем.

Как понять что файл является регулярным или каталогом? Большинство дистрибутивов имеет подсветку при `ls`. Также при выводе `ls -l` первый символ в выдаче будет означать что это за файл, а именно `-` это регулярный файл, а `d` это каталог.

Теперь немного про жесткие ссылки. Про команду `ln` - команда которая нам создает жесткие или символические ссылки. Если мы захотим сделать еще одну ссылку:

``` bash
ln file file_2
```

То в этот момент таблице каталога появится строка, в которой будет уже новое имя файла, но тот же самый ***индексный дескриптор***. Фактически количество жестких ссылок не ограничено (ограничено размерностью и разрядностью лишь). Каждый раз когда создается новая жесткая ссылка, количество жестких ссылок увеличивается на единицу, и эта информация сохраняется а определенном поле индексного дескриптора. Для чего это надо? Вспомним про то что файлы также можно удалять! Здесь возникает интересный момент - если в Windows мы удаляем файл, то сразу записи стерлись, и соответственно определенные блоки данных стали свободными (пометились). В Linux мы так не можем сделать. Если мы скажем:

``` bash
rm file
```

То я не могу удалив запись из каталога, я не могу одновременно освободить i-node и пометить свободными блоки данных, потому что тогда я потеряю и `file_2`, так как он ссылается на тот же i-node и блоки данных. И вот как раз в индексном дескрипторе используется счетчик жестких ссылок, для того чтобы при выполнении команды удаления понять что нужно делать. Если счетчик ссылок имеет не нулевое значение, то выполнение команды `rm` просто стирает запись из таблицы каталога. Если же счетчик ссылок станет равным 0 - то и запись из таблицы каталога удалится, и i-node пометитится свободным + блоки в области data также пометятся свободными. Это позволит использовать эту область для других файлов. Также тут присутствует возможность восстановления файлов. Пока данные блоки не перезаписались и соответствующий i-node не переиспользовался - данный файл еще можно восстановить при помощи определенных утилит. Единственная проблема - это имя файла. Символьное имя хранится лишь в таблице каталога.

*Например Ярлык в Windows ссылается не на структуру данных об этом файле, а ссылается на имя - на полный путь к этому файлу. Есть главный и основной файл, а ярлыки - ссылка на полный путь. При удалении файла полностью удаляются данные, а ярлыки перестают работать.*

Еще один интересный момент связанный с жесткими ссылками. Допустим:

``` bash
mkdir dir1
```

То есть у нас есть жесткая ссылка `file_2` и `dir1` - жесткая ссылка и каталог `dir1`. И теперь я попытаюсь сделать жесткую ссылку на `dir1` как `dir2`.

```bash
ln dir1 dir2
```

И тут я получу, что создавать жесткие ссылки на каталоги создавать **нельзя**. Если зайти в документацию, то там есть ключ, который даст создать жесткую ссылку на каталог. Дело в том что тут можно создать зацикленную структуру каталогов. То есть вместо того, чтобы организовывать иерархию каталогов, сами каталоги начинают образовывать некоторую сеть с циклами - что в общем случае не верное поведение. Поэтому жесткие ссылки на каталоги невозможны. 

*Также тоже есть ошибка в другом моменте. Например если я захочу создать жесткую ссылку на файл например в /.var/log. Например на какой-то журнал. И для простоты хочу сделать жесткую ссылку. И очень часто я получу сообщение об ошибке - о том что var/log будет располагаться на другом разделе - тем самым в другой файловой системе. Я могу сослаться только на те i-node которые принадлежат моей файловой системе, то есть лежат в пределах того раздела, который я использую*

Просто не давайте никому работать под root - а самому думать перед тем, как выполнить подобное действие :)

Теперь введем команду:

```bash
ln -s file2 file3
```

Это символическая ссылка - принципиально другой объект. В каталоге появится `file3` при этом у него будет уже другой i-node - который оказался следующим свободным, который ОС смогла выделить. `-s` - symbolic.

Символическая ссылка очень похожа на ярлык - там же будет храниться просто полный путь к файлу. Это самостоятельный файл с индексным дескриптором, но не будет иметь свое содержимое. Если мы удалим `file2`, то `file3` станет битым, или мертвой ссылкой - он будет подсвечиваться красным цветом при выводе `ls -l`. НО если же мы создадим новый файл `file2`: 

```bash
rm file2
echo "text_2" > file2
```

Если теперь я вывожу содержимое `file3` -> выведется текст "text_2". Также выведется содержимое - достаточно удобный механизм - ссылка на переменное содержимое. Через символическую ссылку уже можно будет обращаться к файлам, которые расположены в других файловых системах, так как это просто ***полный путь к файлу***.

#### Дырки

File - holes - файлы дырки. Что же это такое? Идея в том, что работа с внешними устройствами, которые подключаются к ОС, мы можем работать с ними через интерфейс "файл". В большинстве случае мы используем устройства, чтобы с помощью них читать или записывать данные. Я передаю данные устройствам или я считываю данные. Получается я занимаюсь обменом данными. Для того чтобы обеспечить взаимодействие посредством записи в файл или чтения из файла в Linux есть специальная псевдо-файловая система, которая монтируется в точку `/dev` - devices. Почему псевдо? Там файлы нулевой длины - интерфейсы для устройств. Например там мы можем обнаружить:

- `/dev/mouseN`
- `dev/audioN`

Как работают такие файлы? Чуть позже... Если поверхностно - есть два пути формирования этого каталога - статический и динамический. Статический - изначально создаю много файлов дырок, и если такое устройство такое существует, то я получу к нему доступ, если же нет, то я получу ошибку - но тут я должен хранить огромное количество интерфейсов и понимать как-то доступно данное устройство или нет. Более современный - динамическое создание - существует механизм, который определяет подключенные устройства, определяет драйвера и создает соответствующую точку.

Также необходимо понимать, что помимо того, что мы с устройствами обмениваемся данными (как мы поняли посредством файла - специального интерфейса), мы также отправляем управляющие сигналы, которые позволяют переходить устройству в другое состояние или изменить конфигурацию. Тут уже мы не можем использовать файловые интерфейсы - для этого используются системные вызовы как таковые и утилиты (обертка над системным вызовом).

Но кроме того что в `/dev` есть файлы для предоставления интерфейса для обмена данными с периферией, также там есть файлы, которые определяют виртуальные - несуществующие устройства. Например `/null`. Устройство черная-дыра - все что я записываю в это устройство, пропадает в никуда. Например поток ошибок от какой-то команды я могу перенаправить туда (если мне не нужен вывод в консоль):

```bash
./commnd 2> /dev/null
```

*Когда у нас в Unix подобных системах создается некий процесс, то этому процессу по умолчанию открывается три файловых дескриптора - 0, 1, 2. 0 - stdin стандарный ввод, 1 - stdout стандартный вывод и 2 - stderr стандартный вывод ошибок.*

Также есть устройства `/random` и `/urandom`, которые позволяют генерировать случайные числа - читая из этого устройства и получаю случайный набор значений. `/zero` - читаем нули.

Еще несколько интересных задач:

- `/console` - это устройства которые позволяют получить доступ к консоли
- `/ttyN` - и это тоже

Консоль - совокупность из устройства алфавитно-цифрового ввода (клавиатура) и устройства алфавитно-цифрового вывода (экран с командной строкой). При этом устройство `/dev/console` - это физическая консоль. В Linux физическая консоль должна быть физически недоступна в рамках безопасности. `/dev/ttyN` - виртуальная консоль. Когда загружается операционная система Linux появляется первый сеанс и предложение к аутентификации - далее вводим логин и пароль. В этот момент на самом деле устройство `tty1`, которое отвечает за первую виртуальную консоль, замыкается на физическую консоль. Далее мы вводим команды, и можем много чем управлять. При этом при нажатии `Alt + F2` и так далее мы можем переключаться на другие консоли и соответствующие устройства `/dev/ttyN` которые будут обслуживать эти виртуальные консоли.

Хорошим кончено будет написать перенаправление ошибок второго файлового дескриптора в файл, но иногда файл сильно захламляется, по какой-то причине меня не интересует обработка этих ошибок. удобно их перенаправить в "никуда".

Еще один интересный тип файлов-дырок: `sda`, `sda1`, `sda5`, `sdb`... Эти файлы являются интерфейсами к жестким дискам и его разделам. Сейчас мы используем интерфейс `SATA`, вот как раз и название начинается с буквы S (до этого была еще буква H и буква S ввиду разных интерфейсов). `sda` - доступ целиком к диску, соответственно если у нас множество `SATA` портов, то у нас меняется третья буква - `sdb` и так далее. При этом диск разбит на разделы (корневой, подкачка, каталоги пользователя, раздел под `/var`) -> вот как раз нумерация это номер раздела. Это удобно, так как я фактически могу работать с данными, минуя стандартные приложения или интерфейсы файловой системы.

*К примеру я хочу сделать дубликаты диска. Я настроил один компьютер, полностью поставил все программное обеспечение и не хочу настраивать компьютеры для других. Было бы классно если бы я мог соответствующее устройство настроенное и по сети настроил бы такие же другие устройства копированием. Есть "Acronis", но это дорого. Что я могу сделать без проприетарного ПО?*

У меня есть источник - настроенный компьютер. У меня там есть диск - `sda`.
Есть приемник, на котором также есть диск куда я хочу оформить разливку.

dd - мощная утилита для побайтового копирования и конвертации файлов, блоков данных и образов дисков.

- **`if=`** (_input file_) — файл, устройство или поток, откуда читаются данные.
- **`of=`** (_output file_) — файл или устройство, куда записываются данные.
- **`bs=`** (_block size_) — размер блока (например, `4M`, `512k`), ускоряет работу за счет чтения/записи большими порциями.
- **`status=progress`** — выводит шкалу прогресса выполнения операции в реальном времени.

Команда `ncat` (сокращение от **Netcat**) — это мощная сетевая утилита, которую часто называют «швейцарским ножом» для работы с сетями **TCP** и **UDP**. С ее помощью можно:

- **Проверять доступность портов** на удаленных серверах (замена `telnet`).
- **Сканировать порты** (базовый аналог `nmap`).
- **Переносить файлы** между компьютерами напрямую.
- **Тестировать сетевые службы**, отправляя им сырые (raw) данные.
- **Создавать простые чаты** или прокси-серверы для отладки.

Теперь опишем как это можно сделать:

Сначала настраиваем приемник - открываем порт 1234 и перенаправляем входящий поток на свой диск:

```bash
sudo ncat -l -p 1234 | sudo dd of=/dev/sda bs=4M status=progress
```

Теперь запускаем отправитель. Он читает диск и отправляет поток на IP адрес приемника:

```bash
sudo dd if=/dev/sda bs=4M status=progress | ncat 192.168.0.2 1234
```

Информация на диске приемника полностью сотрется. Он должен быть или равен или больше диска источника.

Вот и пример работы с `/dev/sda`.

Как создать именованный канал? Так называемый `|`. В данном случае (в примере выше) мы создавали не именованный канал, то есть он закроется при завершении одной из команд. То есть мы его никак не сможем использовать по другому. Например есть задача писать в канал с двух консолей (ради примера). Для этого нам нужен будет именованный канал.

```bash
mkfifo c1
```

Вот мы создали канал, выглядеть он также будет как файл - канал это не регулярный файл! А зачем использовать каналы то? Если также можно использовать файлы. Например:

```bash
command1 > file
command2 < file
```

Да и все. Одна пишет в файл, другая читает из файла. То есть так называемый Pipe? Но нет, это достаточно долго и медленно через жесткий диск - постоянно выстраивается очередь на запись данных. А если мы сделаем канал:

```bash
command1 > c1
command2 < c2
```

То тут все взаимодействие пойдет через буфер, находящийся в памяти, тем самым намного быстрее и без особых накладных расходов.

По сути именованный канал это тоже файл "дырка". И Socket тоже является файлом "дыркой" (при помощи команды `ncat` создать именованный Socket).

Также файлы "дырки" делятся на ***два типа***: символьные `c` и блочные `b` (block-устройства). Как раз-таки тип таких файлов "дырок" можно увидеть при помощи `ls -l` к примеру в каталоге `/dev`.

Символьные - устройство работает потоком обмена данных просто по байтам.
Блочные - устройство работает потоком обмена данных с помощью блоков - драйвер обеспечивает формирование и передачу блока целиком и чтение в обратную сторону также блоками. ОС управляет агрегированием.

#### Псевдо-файловые системы

Также в Linux есть псевдо-файловые системы. Они работают по другому принципу. Например `/proc`. Она хранит в себе информацию о всех процессах. Если зайти в нее то мы увидим множество каталогов с числовыми именами, например, `/1234`, `/1638`. Как раз эти имена - `PID`. А если мы зайдем в этот каталог, то увидим множество файлов, которые являются интерфейсами доступа к структурам ядра. Если мы пытаемся прочитать информацию из такого файла, генерируется определенные запросы в ядро - они представляются в виде содержимого этого файла. На самом деле естественно это содержимое нигде физически на диске не располагается.

#### Пример для файлов в Linux

К примеру выполним команду `ls -l` в данной директории:

```bash
total 48
-rw-r--r-- 1 amnesia amnesia  1672 Sep  5 12:02 '0. Введение.md'
-rw-r--r-- 1 amnesia amnesia 11138 Sep  5 12:58 '1. Отличия Linux от других OS в вопросе Администрирования.md'
-rw-r--r-- 1 amnesia amnesia 29236 Sep  7 14:01 '2. Файлы. Понятие работы с файлами..md'
```

Первый символ (может быть `-`, `d`, `b`, `c`) это тип файла. Далее цифра (а данном случае `1`) - количество жестких ссылок - сколько ссылок существует на данный i-node или файловый дескриптор. Далее идет размер файла в байтах (ключами можно изменить формат вывода). Далее идет дата последнего изменения.

Другие блоки относятся к управлению правами на этот файл. Эти права - маска прав и сведения о пользователе и группе - также сохраняются в файловом дескрипторе.

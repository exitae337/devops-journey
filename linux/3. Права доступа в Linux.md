
Вернемся к прошлому примеру вывода команды `ls -l` и посмотрим как реализуются права в Linux:

```bash
total 48
-rw-r--r-- 1 amnesia amnesia  1672 Sep  5 12:02 '0. Введение.md'
-rw-r--r-- 1 amnesia amnesia 11138 Sep  5 12:58 '1. Отличия Linux от других OS в вопросе Администрирования.md'
-rw-r--r-- 1 amnesia amnesia 29236 Sep  7 14:01 '2. Файлы. Понятие работы с файлами..md'
```

В Unix-подобных системах используется модель прав основанная на битах прав доступа. У каждого файла существует три типа. Это доступ для владельца, для группы и для всех остальных. Как раз таки эти три блока можно отследить. Рассмотрим на примере первого файла: `-` (тип файла) `rw-` (owner), `r--` (group), `r--` (other). Владелец - тот кто создал данный файл. Если я хочу изменить владельца файла, то это можно сделать при помощи команды `chown`. Сам я обратно во владение себе файл никак получить не смогу. Только `root` может это сделать обратно или новый владелец.

Когда создается пользователь, одновременно с ним создается группа этого пользователя, в которую изначально входит только он сам. Это механизм позволяющий пользователю создать группу доверенных лиц - те кого он включит в эту группу, им можно давать доступ к файлам и не давать другим доступа (кто не входит в данную группу).

`rwx`:
- `r` - право на чтение (read)
- `w` - право на запись (write)
- `x` - право на исполнение (execute)

*В Linux исполняемость файла это не расширение (которых вообще в Linux нет), исполняемость - это право доступа. То есть я могу дать исполнять файл определенному кругу лиц. Например создать скрипт для себя, который я могу исполнять, а другие например только читать.*

Изменять данные права можно при помощи команды `chmod`.
Есть несколько синтаксических способов изменения прав доступа файла при помощи данной команды:

```bash
chmod u-x file
```

Убрать себе возможность на исполнение.

```bash
chmod g+w file
```

Разрешу группе писать в файл.
Но такой подход не удобен, если надо обработать большое количество файлов. Просто сразу выставить цепочку. Тут уже мы используем ***числа***.

Например маска: `rwx`,`r-x`,`r--` -> `111`,`101`,`100` -> `754`

То есть можно сделать так:

```bash
chmod 754 file
```

Мы сразу установим такие права файлу.

***Как происходит проверка прав?***

Она происходит слева направо. То есть если я пытаюсь выполнить файл, сначала идет проверка того, являюсь ли я `owner`. Если я владелец, то будет проверена первая группа прав. Если нет, то идет проверка дальше.

***Но как обстоят дела с файлами-каталогами?***

Каталог - это просто таблица, которая хранит соответствие символьного имени и ссылки на файловый дескриптор. Так вот право на чтение каталога - прочитать эту таблицу (например при помощи команды `ls` вывести на экран список файлов). При этом `write` - возможность изменять эту таблицу, то есть я не могу добавлять новые файлы в данную таблицу (в данный каталог). Например я имею полные права на файл в каталоге, но только чтение для каталога в котором этот файл находится - соответственно я не могу удалить этот файл, так как у меня нет прав на изменение таблицы. Также я не смогу переименовать данный файл, так как это тоже является изменением таблицы. Последний бит - возможность сделать каталог текущим - при помощи команды `cd` войти в этот каталог (например не могу выполнять различные скрипты в данном каталоге, так как я бит `x` запрещает мне делать данный каталог текущим).

*Также момент про скрытые файлы. В Windows это реализовано при помощи атрибута. В Linux чтобы файл был скрытым - начинаем именование с точки. Это у нас будет условно скрытый файл.*

Права доступа на файл хранятся в файлом дескрипторе в виде числа, так вот кроме 9 бит есть еще два скрытых бита, которые не выводятся при `ls -l`.

#### SUID

`SUID` - бит смены идентификатора пользователя. Когда мы запускаем любое приложение, это программа потенциально может иметь доступ к файловой системе и использовать этот доступ. Раз эта программа может читать и записывать файлы, то возникает вопрос прав доступа к файлам. По умолчанию эти права доступа делаются по правам запускающего пользователя. Когда создается процесс, в Process Control Block этого процесса записывается в том числе идентификатор владельца процесса. И тогда вся деятельность этого процесса в файловых системах происходит от имени этого пользователя. Это приводит к проблеме. Например пользователь хочет поменять свой пароль. Hash хранится в специальном файле. Пользователь и hash его пароля - некоторая строка в этом файле. Тогда для того чтобы пользователь поменял пароль, программа должна получить доступ у этому файлу (на запись). Если я так делаю - то программа имеет доступ и к другим записям в данном файле. При этом давать возможность только суперпользователю менять пароли тоже странно, особенно при большом количестве пользователей. Хорошим тоном является то, чтобы и системный администратор также не знал пароля пользователя. Системный администратор вправе сбросить его, изменить на другой, но исходный он не должен знать. Как же дать такие права пользователю - чтобы он мог получить доступ к файлу с паролями, но не мог воспользоваться данным файлом, кроме как для решения насущной проблемы с изменением пароля.

Как раз для этого и нужен данный бит `SUID`. Если данный бит равен 1 и при этом бит `x` для `other`, то при запуске такого файла (программа, скрипт, приложение) получает доступ к файловой системе не по пользователю и его правам, а по владельцу этого файла. Если владелец `root` и установлю бит `x` для `other` в `1` и соответственно подниму `SUID` бит в `1` то тем самым при запуске такого файла он будет иметь доступ к нему по имени владельца данного файла, то есть от имени `root`. Хм, ну это может опасно? Нет - главное правило, чтобы при запуске такого файла бит `w` для `group` и `other` не был установлен в `1`.

#### SGID

Аналогично работает и `SGID`, но он в отличие от предыдущего позволяет делать запись от имени группы владельца. То есть принадлежность будет проверяться не по пользователю, который запустил данный файл, а именно по группе, к которой принадлежит данный пользователь. Реже используется, но такой способ есть и может использоваться.

#### Sticky bit

Липкий бит? Почему он липкий? Данное название исторически появилось для другой задачи, которая была актуальна для задач для старого ядра Linux - сейчас использование данного бита поменяли, а название осталось с тех времен. Очень часто при создании скриптов мы используем одни и те же команды, программы. Проблема упирается в производительность - каждый раз когда мы запускаем приложение, код его запускается в оперативную память (в выделенное пространство для данного процесса), и только потом он становится в очередь в планировщике и только затем при подходе его очереди на исполнение данный код начинает исполняться. НО что получается один и тот же процесс (например мы выполняем много раз `grep` в скрипте) много раз загружается и выгружается из памяти. Естественно это связано с нагрузкой. Поэтому была идея такие утилиты помечать таким битом - ОС однажды загрузив в память соответствующий файл оставляет в памяти эту область, зафиксированную за этим файлом и после того как процесс завершается, эта область не освобождается - там продолжает находиться код этой программы. Тогда в результате повторного запуска не нужно быть снова грузить код в память. Просто сопоставим адреса процесса с данной областью памяти и будем выполнять.

***НО достаточно быстро было понято***, что такой подход имеет различные уязвимости по безопасности. Потому что мы оставляя в памяти фиксированную область либо должны сохранять защиту этой области (не рационально - нет оснований что когда то он еще будет запущен).

В более старших ядрах Linux от этого отказались, и если мы сейчас будем устанавливать данный бит в `1` для регулярного файла - в результате для данного файла это значение будет проигнорировано. Но тем не менее он сейчас используется для **каталогов**. Для работы с каталогами эта модель оказывается грубой и не удобной если я хочу создавать каталоги для обмена данными между ***собой***. Если для каталога я установлю такой бит в `1`, то это будет означать, что создавать в данном каталоге файлы кто угодно может (бит `w` для `other` тоже поднят в единицу), а вот удалять их сможет только создатель или `root`.

#### Дополнительные атрибуты

У файлов в Linux также как у файлов в Windows есть атрибуты. Команда `chattr` как раз-таки служит для того, чтобы эти атрибуты менять. Имеют специфический функционал. Например:

- `chattr +i file1` - запрет на изменение, переименование и удаление файла. Избегание случайных действий - например случайное удаление. Менять данный атрибут может только `root`.
- `chattr +a file1` - позволяет управлять доступом к текстовым файлам - разрешает только дописывать информацию - например удобно для создания журналов. Например команда `echo 'a' > file` не сработает, а команда `echo 'a' >> file` сработает, так как тут мы лишь дописываем информацию в конец файла.
- `chattr +j file1` - для журналирования. Когда мы совершаем действия с файловой системой, сначала мы создаем журнал, и только после переносим действия из журнала в "реальность". Очень часто журнал будет отключаться. Данный атрибут принудительно призывает использовать журналирование для данного файла.
- `chattr +S file1` - синхронная запись. По умолчанию используется отложенная запись в файл. То есть файл записывается не когда я дал на это команду в программе, а через некоторое время. Это объясняется тем, что ведь изменения в файле могут происходить например очень быстро и друг за другом множество одинаковых операций - как раз лучше разом все это в памяти сохранить и разом обработать (кеширование). `+S` требует чтобы каждая попытка сохранения синхронизировалось с хранилищем.
- `chattr +s file1` - занулять файл при удалении. При таком флаге файл не остается в битовой карте - при простом удалении данные можно восстановить.

Теперь перейдем на более низкий уровень -> от файлов к тому как они располагаются и как организуется к ним доступ - к файловым системам.


### Что такое ветвление в git и для чего вообще это нужно?

Ветвление это механизм, при помощи которого можно отойти от главного "пути" разработки приложения и продолжить внедрение функционала независимо от главной линии разработки. То есть если в голову пришла фича, лучше сделать ее в другой ветке, не трогая основную (`main` или `master`).

Git хранит данные в виде снимков. Каждый снимок представляет набор ссылок на файлы из ранних версий и на те файлы, которые изменились - он не хранит набор дельт. Когда мы делаем коммит, git сохраняет коммит в виде объекта, который хранит в себе набор определенных данных + ссылку на определенный снимок. Объект коммита также харнит в себе информацию об авторе, комментарий и указатель на предыдущий коммит или несколько (если происходило слияние).

``` Example
commit size
tree 56cer
author Max
comitter Max
```

То есть структура в конечном счете прдставляет из себя объект коммита, который содержит ссылку на снимок. У самого первого коммита указателя на предыдущий коммит нет. Поэтому мы можем "**откатываться**".

#### А что же тогда такое ветка?

Ветка это простой указатель на какой-то из коммитов. Например ветка master это просто указатель на коммит. Когда мы инициализируем репозиторий при помощи команды `git init`, то git по умолчанию создает ветку master. Она не является какой-то особенной. Master это такая же ветка как и другие. Каждый раз когда мы делаем новый коммит на ветке master, то указатель смещается на самый последний сделанный **commit**. Но не обязательно master будет указывать на последний сделанный commit.

*А что же тогда такое - создание новой ветки?*  Это просто создание нового указателя, только с другим именем. Новая ветка создается при помощи команды:

``` bash
git branch test
```

После такой команды создастся ветка test. После при помощи команды `git log --oneline` можно посмотреть на изменения (`--oneline` используется для более понятного отображения лога).

Если же мы хотим создать ветку и сразу на нее переключится, то используем другую команду:

``` bash
git checkout -b test_1
```

Просто для переключения на другую ветку используем `git checkout test` - то есть без флага `-b`.

*А как git узнает на какой ветке мы сейчас находимся?* Для этого существует указатель `HEAD`. Он как раз и указывает на какой ветке мы находимся - то есть куда будет попадать следующий коммит.

И как раз после создания новой ветки, создается новый указатель. Например делаем новую фичу, сделали и создали новый коммит на ветке `test`. Указатель `test` сместится. Указатель `master` останется на том же коммите, на котором и был. В этом и преимущество оперирования ветками при разработке новых фич - локально тестируем проект с новыми "идеями", не трогая основную линию разработки. Если захотим - откатимся.

#### Слияние веток

Например, у нас есть `master` ветка - основная линия развития и разработки нашего приложения. Также есть ветка `feature`, где мы реализуем доп. функционал, который теперь после успешного тестирования хотим влить в `master`. Что для этого нам надо сделать? 

Но тут кстати можно упоминуть такую вещь. Если например ветка явялется прямым потомком ветки `master`, например есть ветка `feature_1`, которая явялется прямым потомком основной ветки. При этом вызов команды `git merge feature_1` добавлял изменеия сделанные в данной ветке в master простым передвижением этой ветки master (просто "передвижение" указателя master). Это называется слияние - перемотка.

Но что если ветка feature не является потомком ветки master. То есть на определенном коммите данная ветка появилась, а master сам пошел дальше, и имеет свои коммиты. Каждая из них имеет свои собственные независимые коммиты. Просто передвинуть указатель на комиит, на который указывает feature не получится, ведь собственные коммиты master просто "пропадут".

При таком случае git использует истинное слияние, при котором изменения в каждом файле анализируются, объединяются и создается новый коммит, который содержит как изменения с одной ветки, так и с другой.

Перед слиянием, рекомендуется чтобы `status` был чистый.

```bash
git status
```

Теперь посмотрим при помощи команды `git diff` разницу между двумя ветками. Флаг `--name-only` позволяет вывести только имена файлов, без собственно различий.

```bash
git diff --name-only master feature
```

Для запуска слияния используем команду:

```bash
git merge feature
```

1. После запуска данной команды git начнет искать общего предка двух веток - то есть тот коммит, где ветки разделились. Если мы забыли и не помним когда произошло данное разделение, можно спокойно посмотреть общего предка двух веток:

```bash
git merge-base master feature
```

2. Потом для каждого файла сравниваются его три версии. Первая - которая была в общем предке (base), вторая - которая на текущей ветке (ours), и третья которая из другой ветки (theirs), в данном случае из feature.
3. Git далее пользуется "формулой": `base + (our changes) + (their changes) -> merge`.

Тут может возникнуть проблема, если мы меняли один и тот-же файл в разных ветках. В данном случае git спросит нас о том, что из этих двух изменений - правильно.

При звпуске 

```bash
git merge feature
```

Если мы получаем конфликт, например файл `sas.txt` менялся и в одной и другой ветке, нам  git об этом скажет - возник конфликт. То есть git поброует слить две ветки, но при этом заметит, что в файле `sas.txt` были изменения в обоих ветках, в одном и том же месте - git не знает что с этим делать. Такое состояние называется "***прерванным слиянием***". Git запоминает коммит с которым осуществляем слияние в файле MERGE_HEAD

```bash
cat .git/MERGE_HEAD
```

Тут мы следуя примеру получим коммит, на который указывает ветка `feature`.

***Попробуем разрешить конфликт и завершить слияние***

Если файл менялся только в одной из веток, то берется в индекс именно эта версия файла из соответствующей ветки. Например если файл `pop.txt` менялся только в ветке feature, то оттуда и будет браться последняя версия для слияния. Данный файл из ветки feature будет просто добавлен в индекс. Но что же делать с файлом `sas.txt`?

Но тут также есть варианты. Например если данный файл 

В base выглядит так:

```sas.txt
Hello
From
Keks!
```

В ветке `master` выглядит так:

``` sas.txt
Hello
From
Max!
```

А в ветке `feature`:

```sas.txt
Bye
From
Keks!
```

То никаких конфликтов не будет. Данный файл при merge будет выглядеть так:

```sas.txt
Bye
From
Max!
```

Тут все просто. В одной и второй ветке затрагиваются разные измения. Но если в одной и второй ветке меняется одна и та же строчка. Напрмиер в одной передается привет `Max!`, а в другой `Masha!`,  то тут как раз и воникает конфликт! Git не знает что делать.

Для того чтобы посмотреть какие именно изменения произошли в одной и другой ветке, и чем они отличаются от base, можно использовать следуюшую команду:

```bash
git diff -U0 base master sas.txt
git diff -U0 base feature sas.txt
```

При выводе мы увидим, что надо сделать и на каких строках чтобы вернуться к базовой версии. Как раз данные команды могут позволить нам понять, что в данных файлах приветы передаются разным людям (третья строчка противоречит друг другу ).

Также многие редакторы показывают конфликты. Например так:

```txt
Bye
From
<<<<<<<< HEAD
Max!
=======
Masha!
>>>>>>>> feature
```

То есть тут нам редактор подсказывает что на нашей ветке master `Max!`, а на ветке feature `Masha!`. Пусть например правильная версия данного файла находится в ветке master. Для этого подтянем изменение из ветки master (HEAD):

```bash
git checkout --ours sas.txt
```

В данном случае git вытащит тот файл, который соотвествует состоянию на master. Но бывает и наоборот. Для этого:

```bash
git checkout --theirs sas.txt
```

После того, как мы определились с тем, что именно нам актуально. Передавать привет Маше или Максиму, продолжаем слияние:

``` bash
git checkout --merge sas.txt
```

После данной команды мы получим версию с маркерами конфликта, как выше.
Также мы можем сказать, что нам слияние уже не нужно, верни как было.

```bash
git reset --hard
```

Это очистка всех не закоммиченных изменений, включая конфликты.

Вернемся на предыдущую версию (самую начальную), без очистки индекса коммитов (которые были сделаны на тот момент):

```bash
git merge --abort
```

Или

``` bash
git reset --merge
```

Но мы же не будем поднимать руки вверх и довоедем слияние до конца?

Также для полного понимания картины конфликта, можно запросить то, что было в base версии в данном месте. Например:

```txt
Bye
From
<<<<<<<< HEAD
Max!
|||||| base
TODO!
=======
Masha!
>>>>>>>> feature
```

То есть на данном примере в base вместо передавания приветов был текст `TODO!`.
Это делается командой:

```bash
git checkout --conflict=diff3 --merge sas.txt
```

Если такой формат представления конфиктов нравится, то можно изменить конфигурацию:

```bash
git config --global merge.conflictStyle diff3
```

После того как мы это все увидили, меняем файл на тот, который считаем нужным в ручную. Например на:

```sas.txt
Bye
From
Max and Masha!
```

Но, если мы запустим commit, все равно ничего не выйдет, так как в индексе хранится три вида файла (конфликт).

Какие именно версии можно посмотреть с помощью команд (base, ours, theirs):

```bash
git show :1:sas.txt
git show :2:sas.txt
git show :3:sas.txt
```

Это покажет как раз три версии файла.
Для разрешения конфликта, просто добавляем в индекс наш исправленный файл:

```bash
git add sas.txt
```

После этой команды вызов `git status` покажет что конфликтов нет, и можно спокойно коммитить. Для завершения слияния просто коммитим изменения, или командой:

```bash
git merge --continue
```

Это просто псевдоним, который работает только из состояния слияния.

Никому приветы передавать не буду! Тестирую разрешение конфликтов merge!
